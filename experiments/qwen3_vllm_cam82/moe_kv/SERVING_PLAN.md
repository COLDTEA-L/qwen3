# 原生PD服务的MoE与KV重叠验证计划

更新于2026年10月22日。目标是用真实模型请求产生必要的KV传输，验证它与MoE是否重叠，以及同工作量调度能否改善TTFT、TPOT与SLO。七组已完成重放结果见 [RESULTS.md](RESULTS.md)。本文件是后续实现与实验计划，不是已经可执行的新测试脚本；本次不修改模型通信或启动额外搬运。

## 1 主实验不注入多余KV

保留228卡0～3为P4、228卡4～7与238卡0～3为D8，TP4、DP2、EP8；238卡4～7不加入实验。原生off TP、原生MoE、原生Mooncake，先禁用prefix caching以保证必要搬运可解释。模型、tokenizer、镜像、代码、随机种子及网络配置固定。

对同一份请求清单和到达时序比较：

- U：原生P/D调度，包含业务必需的正常KV传输。
- C：相同业务工作量，只改变必要KV的提交节奏，例如有界等待、分块或限速。先验证重叠与影响，再实现这组。
- U0：同版本无测量埋点，与启用轻量埋点的U比较，用于测量观察开销，不是无KV基线。

不丢请求、不跳过KV、不减少输出、不把未完成的KV移出计时窗口。相同目标输入输出长度、请求顺序和计划到达时刻；实际完成token数和KV字节仍须核对。已有请求的TPOT改善必须与新请求TTFT、KV等待和完成时间一起报告。

“仅长输出”对照可帮助发现现象，但它与混合请求的工作量不同，不能用作控制器收益的正式基线。SERIAL重放不是可直接复制到serving的策略；等待所有decode结束才搬KV可能饿死新请求。

## 2 请求负载的三层选择

### 第一层 可控真实模型请求

使用真实P/D服务与普通文本请求，但由固定脚本安排长度和到达时间。不是通信重放，也不注入无业务需求的KV。用于建立可重复因果链，不声称代表生产分布。

| 请求类 | 输入token目标 | 输出token目标 | 作用 |
|---|---:|---:|---|
| 长输出请求V | 128 | 512 | 维持已有decode，观察TPOT和输出停顿 |
| 长输入新请求N | 1024，随后单独测试1536 | 32 | 完成P prefill后触发必要KV搬运 |
| 普通请求R | 256 | 128 | 后续稳态混合负载，不在首轮同时加所有因素 |

按Qwen tokenizer及实际chat template计数，输入+输出不超过2048。保留prompt哈希、实际token数、采样配置；文本来自固定多样化段落，覆盖问答、摘要、代码解释，不重复同一句填满所有请求。MoE路由可能受内容影响，因此即使长度相同也要固定内容，并按多组内容种子复测。可控容量实验使用固定生成长度及ignore_eos时必须注明；另做正常EOS的正确性与代表性检查。

首轮只启动约2个V请求/DP，总计4个；普通服务每DP最大4条时预留新请求进入的空间，不一开始用V占满所有槽位。先观察两个DP确实有decode，再提交一波N（先2～4个）。若全被排队而无KV与decode重叠，这是调度行为结果，需记录，不靠伪造搬运解决。

执行顺序：

1. 完成P、D、代理的正确性、成功KV搬运、两DP路由检查；清除QWEN_MOE_CAPTURE_DIR，停止独立重放，不让两者共占设备。
2. 预热模型和连接。用无profiling预跑确定V能覆盖突发前后足够时间。
3. 生成固定请求manifest：相对到达时间、唯一request_id、prompt/哈希、目标输出、业务类别、种子。正式U/C对照使用相同固定时序，不根据各组响应速度临时调整到达。
4. 先发V，在预跑确定的时刻发N；为观察重叠可以做短条件触发诊断，但不能把不同策略下自适应到达的诊断当作同负载对照。
5. 等所有请求和KV完成。突发波次结束后再开始下一轮，避免把上轮遗留工作混入下一轮。

逐档探索V并发、N突发大小，先2～4，再8、16，只有在容量、错误率和实际batch确认后再考虑32。修改服务最大并发要单独加明确服务压测开关并保留容量检查，不能用现有capture-load-test长期运行；该开关依赖采集目录，会把测量与元数据采集混在一起。真实服务暂不直接照搬128请求采集配置：128×2048超过当前固定KV预算，而1024服务上下文又容不下1536-token输入请求。先在完整2048上下文、小并发下发现重叠。

### 第二层 公开生产分布驱动

推荐Azure LLM inference trace 2023的Conversation、Code子集。它给出调用时间、输入token数和生成token数，但不含原始prompt。因此这是“生产到达与长度分布驱动的请求”，不是原始业务内容重放。[数据说明](https://github.com/Azure/AzurePublicDataset/blob/master/AzureLLMInferenceDataset2023.md)

选择固定连续时间片，保存数据版本、校验值、抽样种子；保留输入长度、输出长度与到达间隔的联合关系，不分别随机采样三个边缘分布。将到达间隔按一个预先固定比例缩放到16卡可承载范围，报告该比例；不要把缩放后的RPS说成原始生产负载。

当前上下文2048限制下，主分析只用总长度可容纳的请求并报告排除比例和过滤后分布；不要静默截断。若做长度缩放或分桶，作为另一个明确标注的敏感性实验。输入内容用固定、脱敏的多样化语料构造，经本机tokenizer核实长度；不沿用数据说明中“内容不影响性能”的一般性假设，因为此处MoE专家路由可能随内容变化。没有原始prompt时不能宣称复现原生产专家路由。

到达采用open-loop计划，不用“前一个请求结束才发下一个”掩盖拥塞；客户端保护上限若导致延迟发送，单独记录scheduled_at、sent_at、client_queue和未发送/超时数。策略对照保持到达manifest完全相同，不丢弃慢请求。

### 第三层 用户实际业务trace

如能提供脱敏记录，用request_id、到达时间、实际输入输出长度、会话/任务类别、优先级、SLO与缓存命中信息驱动。没有这些信息时，不称为agent workload；Azure trace同样不能自动证明agent恢复场景。真实多轮KV复用与prefix cache命中作为后续扩展，不能与当前关闭prefix caching的对照混淆。

先用可控请求验证方法，再用生产分布验证普适性，有真实业务数据再补业务代表性。不建议先引入多个复杂数据集，造成长度、内容、时序同时变化而难以解释。

## 3 分阶段实验和通过条件

| 阶段 | 改动 | 产物与通过条件 |
|---|---|---|
| S0 正确性和路由 | 恢复原生P4+D8，无额外KV | 两DP都响应正确，必要KV成功，记录本机/跨机路由；确认代理有无重算回退及首token来源 |
| S1 观察开销校准 | opt-in轻量埋点，无额外同步 | U0与U的吞吐/延迟误差、日志量、丢事件率；显著扰动则先减负 |
| S2 小突发重叠发现 | 固定V+N请求，短profile | 业务请求→KV→设备任务，以及batch→MoE→设备任务的可审计关联；无重叠也如实报告 |
| S3 无profile性能复测 | 多次相同manifest，低/中/高负载 | TTFT、TPOT、输出间隔、队列、吞吐与成功率；至少5次独立运行/种子，避免把相关token当独立样本 |
| S4 同工作量策略对照 | 经验证的有限等待/分块策略C | 同请求集、完成token、必要KV字节；评估MoE和KV双方、整体SLO与goodput |
| S5 生产分布验证 | 固定公开/用户trace | 固定配置和预先指定负载倍率，报告过滤/缩放以及是否仍有重叠与收益 |

不用单次慢请求或只看最坏窗口证明因果。观察到“KV期间token更慢”只是关联：batch大小、decode位置、prefill混入、专家路由、计算与排队都可能变化。先按这些特征分层匹配；真正调度收益必须来自U/C同工作量对照。有限延迟策略优先采用有界的传输准入和可验证完成反馈，不能仅用瞬时is_moe_active布尔值锁住整段KV，它既不保证设备无重叠，也可能造成饥饿。所有策略需期限、超时与回退。

成功标准不是必须超过某个预设劣化百分比。若真实服务无明显重叠或端到端影响很小，记录适用边界；不能增添无必要KV使结论变大。

## 4 端到端指标与关联标记

### 指标

- 客户端TTFT：从实际发送到第一个有内容的响应。另报计划到达至首响应的延迟，包含客户端排队。
- 明确代理首token来自P还是D；若P首token在KV完成前已返回，客户端TTFT不一定包含KV等待，须另报首个D输出时间及首token后停顿。不要把所有TTFT统一解释为P+KV+D。
- TPOT：保留当前平均TPOT，同时记录输出时间序列。SSE chunk不保证一token，chunk间隔只能称为客户端输出间隔；设备token级ITL来自调度/生成步标记，不能用chunk数替代token数。
- 新请求KV准备等待、搬运本身时长、完成时间；已有V请求和新N请求分别统计。
- E2E、完成吞吐、token吞吐、实际输出长度、错误/超时、运行/等待队列、每DP实际batch、必要KV字节及本机/跨机比例。
- 预先约定业务TTFT/TPOT deadline后统计SLO达标率和goodput；没有业务SLO时报告多阈值曲线，不臆造“达到生产SLO”。
- 常规报告p50/p95；P99至少收集足够多请求或突发重复（建议先1000请求级样本，并报告样本数及独立重复区间），不把200或1000当作自动可靠的保证。

### 关联链

以统一run_id加关联表维护三条链，禁止只靠名字或最近时间邻居硬匹配：

1. client request_id → proxy内部ID → P请求ID → D请求ID → 实际KV transfer_id及源/目的device、字节、ret。
2. D scheduler_step/batch_id → 该批请求列表、prefill/decode token数 → 层号、EP group、collective序号 → Dispatch或Combine。
3. Host标记 → CANN API correlation/connection或flow → stream/task及设备活动；保留关联来源和置信等级。

多个请求共享同一MoE batch，不把整个MoE时长重复归因到每条请求。收集请求ID映射而非原始prompt全文，避免日志泄露。从线程/进程本地缓冲异步批量落盘，计时热路径不打印海量日志，不加torch.npu.synchronize或新barrier。

原生KV后台线程的计时应包住实际batch_transfer_sync_read；排队、远端元数据握手及成功完成分别记录。请求列表/分片尺寸等由已有CPU元数据获取，不为埋点新增设备到host同步。既有stream上的异步event只有在接口和生命周期验证后再用；不能用default stream事件冒充传输引擎的专用stream时间。

## 5 不依赖肉眼的短窗口profiling

### 先验证旧版本能力

当前固定vLLM Ascend v0.10.2rc1的worker_v1.py已用VLLM_TORCH_PROFILER_DIR初始化profiler，显式Level1、Text导出，并有profile(is_start)启动/停止方法。源码位置约296、329行。它不同于较新版本的profiler-config参数，实施时必须按容器实际源码核对，不能照抄新文档。

先用一次小请求验证控制端点如何广播到两个DP的所有worker，确认不会重复start、遗漏远端rank或在stop时阻塞；API可用不等于全EP已采集。KV原生线程、CANN层标记能否进入导出文件也需先验证。

官方建议通信小算子采集采用Level1以上；工具可输出通信时间和矩阵，但业务上的“KV与MoE”分类仍需自己的关联标记。[通信分析采集要求](https://github.com/Ascend/msprof-analyze/blob/master/docs/en/user_guide/cluster_analyse_instruct.md)

### 长测试用轻量日志 短测试用设备采集

- 正式性能run不开设备profiler；只保留必要且已测量开销的轻量记录。
- 诊断run复用相同请求manifest，预热后仅在突发前后收集约3～5秒，或固定20～40个模型step；二者是候选窗口，按预跑调整，不把请求数当profiler step数。
- 每个run选择约3个预先定义的突发窗口，输出各自window_id、开始/结束ack与时间边界。小KV可能在触发profiler前已经结束，所以优先在计划突发前预先启动，而不是看到KV完成日志才开始。
- 若传输跨越窗口，标记left/right-censored，延长下一次窗口；不把截断末尾当真实完成。保存完整性、丢失事件、rank覆盖和关联成功率。
- 起步采集D侧EP8，保证跨rank的collective序号可配对；分析先聚焦238卡0～3并按设备求交集。只采rank08的小样本可检查文件格式，但不能宣称得到了EP8的关键路径。
- 不启用无关的调用栈、内存追踪、全量形状/参数及无必要PMU；通信细节必须保留。设定文件大小和持续时间上限，达到上限正常停止并标注未完成覆盖，不删除原始结果。

### 自动分析的具体设计

先检查当前环境真实导出格式，再实现适配器。优先兼容现有Text输出的trace_view/msprof JSON、communication JSON及实际可用的CSV；不能假定新版SQLite表在CANN8.2中必然存在。输出字段应统一为host、device、pid、tid、rank、group、seq、start/end、stream/task、business_id、evidence_level。

关联时使用导出的flow/correlation/connection_id及已验证的线程/stream上下文；未能唯一归属的事件保留unknown，不将所有RdmaDbSend归为KV。CANN文档定义connection_id用于API与NPU算子的关联，通信细节可含src/dst、大小、链路和stream/task；具体可用字段以本机导出为准。[性能数据字段参考](https://mstt.readthedocs.io/en/latest/msprof/source/user_guide/profile_data_file_references/)

证据分层输出：

- H：Host同步搬运调用区间与MoE Host调用/等待区间重叠，只是候选。
- D：已关联的设备任务执行区间重叠；门铃提交本身单独标为doorbell_only。
- T：有明确传输活动/完成语义支持的区间重叠；仍不自动等于某物理链路带宽冲突。
- L：结合资源路径、端口/链路计数器支持共享资源竞争。若接口不暴露完成信息或计数器，停留在较低等级，不能用“最早门铃～最后门铃”填成已验证的整批传输区间。

同一host同一设备、已统一时钟域的活动先去重：将一类区间取并集，再做扫描求交。不能把所有事件两两交集直接相加，也不能同时计入父collective和其子任务造成重复。跨host未经校准的monotonic时间禁止直接相减；host-device时间用工具提供的关联对齐，残余误差应记录。

自动指标至少包括：

- MoE活动覆盖率 = MoE与KV设备活动并集的交集时长 / MoE活动并集时长。
- KV活动覆盖率，同样定义但分母为KV活动并集。
- 发生重叠的MoE调用比例，与“时间覆盖率”分别报告。
- 每个request/batch/layer/rank的关联、重叠量、通信耗时、实际字节；无法关联/截断占比。
- 重叠与未重叠调用的耗时，按层、shape、split或字节区间、batch、decode位置分层；不把不同大小消息直接比较为劣化。
- 请求TTFT/输出间隔/TPOT与转移窗口的关联表；客户端时钟和服务器不同域时使用ID和校准关系，不直接比较绝对时间。

### MindStudio只做抽查

计划生成以下文件，均为待实现的交付物：

- overlap_summary.json / report.md：总覆盖率、证据等级、未关联比例和边界说明。
- overlap_events.csv：每条重叠的request_id、batch/layer、rank/device、起止时间、时长、关联证据。
- request_metrics.jsonl：请求类别、队列、TTFT、TPOT、输出间隔、失败与KV时间。
- review_windows.json及小型裁剪trace：固定种子随机样本、代表性中位重叠窗口、最慢窗口、无重叠对照，各若干条；不能只给最坏个例。
- rank与窗口清单：告诉用户打开哪个文件、哪张卡、哪个时间段、哪些stream，而不是让用户搜索整份trace。

裁剪保留必要metadata和flow端点并附时间偏移；不支持裁剪导入时仍保留原文件并给精确书签时间。自动分析应有区间交集、去重、单位、截断、clock域、错误归属和缺失flow的合成测试。人工抽查用于验证分类与时间语义，不能替代全样本统计。

## 6 实现顺序与验收

本次仅保存计划与已有数据，不实现以下模块，也不启动任何实验：

1. workload manifest生成和流式请求驱动：固定请求/时序、两DP路由观察、长度校验、实际输出记录、失败不丢弃。
2. opt-in服务关联埋点：代理ID、调度batch、原生MoE和KV；验证不新增同步、不改变算法与请求完成语义。
3. 有界profile控制与文件清单：确保跨worker覆盖、预先启停、小窗口、失败可停止。
4. 离线重叠分析：先用一个真实小样本确定字段，带合成测试和人工标注抽查；输出unknown而不是强行认定KV。
5. 小负载S0～S2通过后，再做S3性能矩阵；只有观察到必要KV与MoE重叠且有端到端影响，再评估S4调度。
6. 最后生产分布和多种prompt内容复测。样本、策略和阈值预先登记；公开报告保留无收益和失败边界。

若需要物理链路归因，额外核实每个rank端口/路由及可用计数器，不承诺当前A2/CANN版本支持所有新工具特性。统一控制器价值的最终证据应是同业务工作量下的SLO或goodput改进，而不是只证明额外背景流量可以拖慢算子。
